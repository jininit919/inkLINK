### Detailed findings

#### 1. Charge type — **Partial**

There is **only one `stripe.PaymentIntent.create` in the entire codebase**, at [server.py:6425](server.py:6425), inside `_create_balance_charge()`. This handles the **balance** charge (post-tattoo top-up).

**The deposit PaymentIntent is never created server-side.** [`POST /api/bookings`](server.py:4972) writes a row with `status='pending_payment'` and `stripe_payment_intent_id` left NULL. The frontend has no Stripe Elements / Checkout flow to redirect to. **Currently every "live" booking sits forever in `pending_payment`** unless the cancel flow auto-confirms it (it doesn't).

This is the **single most critical gap**: the entire deposit-collection path is non-functional in live mode. Demo mode hides it (booking jumps straight to `confirmed`) but production would silently lose every booking.

#### 2. Connect setup — **OK**

Express accounts with explicit capabilities at [server.py:7569–7584](server.py:7569):

```python
stripe.Account.create(
    type='express', country='CZ', ...,
    capabilities={'card_payments': {'requested': True},
                  'transfers':     {'requested': True}},
    business_type='individual',
    business_profile={'name': ..., 'mcc': '7299'},
    metadata={'inklink_user_id': ..., 'inklink_username': ...},
)
```

`AccountLink.create` for onboarding (`refresh_url` / `return_url` correctly wired). `account.updated` webhook syncs `charges_enabled` / `payouts_enabled` / `details_submitted` back to the user row. `account.application.deauthorized` clears the link.

#### 3. Escrow pattern — **Partial — needs work**

Currently using **destination charges** with `application_fee_amount`:

```python
# server.py:6425–6435 (balance charge)
stripe.PaymentIntent.create(
    amount=cents,
    currency=(b['currency'] or 'CZK').lower(),
    application_fee_amount=fee_cents,
    transfer_data={'destination': artist['stripe_account_id']},
    metadata={'inklink_booking_id': ..., 'inklink_kind': 'balance'},
)
```

**Problems:**
- **Not true escrow** — funds settle directly into the connected account immediately. There is no hold/release pattern. For a marketplace where the tattoo is performed *after* deposit, this is incorrect: if the artist no-shows we'd want the platform to claw back; with destination charges the money is already at the artist.
- The spec asks for **separated charges + delayed transfers** (`stripe.PaymentIntent.create` to platform balance with `transfer_group=...`, then `stripe.Transfer.create` once the booking completes). Current code is incompatible.
- For the deposit leg (not yet implemented), there is no design decision recorded.

#### 4. Idempotency keys on mutations — **Broken — only 2/6 sites**

| File:line | Call | Has `idempotency_key`? |
|---|---|---|
| server.py:5598 (cancel_booking) | `stripe.Refund.create` | ✅ `f'cancel-{bid}-{actor}'` |
| server.py:6204 (decide_refund_request) | `stripe.Refund.create` | ✅ `f'rrq-{rid}'` |
| server.py:6425 (_create_balance_charge) | `stripe.PaymentIntent.create` | ❌ |
| server.py:7569 (connect_onboard) | `stripe.Account.create` | ❌ |
| server.py:7589, 7616 (connect_onboard / refresh) | `stripe.AccountLink.create` | ❌ |
| server.py:7659 (connect_login_link) | `stripe.Account.create_login_link` | ❌ (acceptable — non-mutating) |

The refund flow added in this week's work uses idempotency keys correctly. Everything else does not. Retry of `_create_balance_charge` would create a duplicate PaymentIntent.

#### 5. Webhook signature verification — **OK**

[server.py:7706–7710](server.py:7706):

```python
payload = request.get_data()            # raw bytes
sig = request.headers.get('Stripe-Signature', '')
if STRIPE_WEBHOOK_SECRET:
    event = stripe.Webhook.construct_event(payload, sig, STRIPE_WEBHOOK_SECRET)
```

`request.get_data()` returns raw bytes (not parsed JSON) → correct. The dev fallback that parses JSON without verification when `STRIPE_WEBHOOK_SECRET` is empty (line 7713) is **insecure if accidentally left enabled in prod** — should either fail loud or refuse to accept anonymous webhooks at all.

#### 6. Webhook event deduplication — **OK**

`processed_stripe_events` table created at [server.py:951–955](server.py:951). The handler inserts `event_id` *before* processing (line 7727); on UNIQUE violation it returns 200 OK and skips ([server.py:7732](server.py:7732)). Correct pattern.

#### 7. Booking state machine — **Missing**

Status values found by grep:
- `pending_payment` (initial in live mode)
- `confirmed` (after payment or demo creation)
- `completed` (artist marks done)
- `cancelled_client` / `cancelled_artist`
- `no_show`
- `refunded` (set by webhook handler at [server.py:7852](server.py:7852))
- `disputed` ([server.py:7877](server.py:7877))
- `payment_failed` (referenced in webhook handler but not consistently set)

These are **scattered string literals**, written directly in `UPDATE` statements at ~20 sites. There is no enum, no allowed-transitions table, no validation. It is currently possible to transition `completed → pending_payment` if a webhook arrives out-of-order; nothing prevents it. Spec calls explicitly for a state machine — none exists.

#### 8. Refund flow — **Partial**

- `cancel_booking` ([server.py:5588](server.py:5588)) — auto-refund based on hours-before tier (96 h = 100 %, 48 h = 50 %, < 48 h = 0). **Just gained Stripe refund call this week** (we shipped it today).
- `refund_requests` table + UI ([server.py:6022](server.py:6022)) — client requests, artist/admin decides, on approve calls `stripe.Refund.create` with idempotency_key.
- `charge.refunded` webhook ([server.py:7838](server.py:7838)) — writes `economics_snapshots` row with `kind='refund'`, updates booking to `status='refunded'`.

**Gaps:**
- Refund fee modelling: Stripe's processing fee is **not refunded** by Stripe. Code captures a heuristic 1.5 % + 6 Kč ([server.py:7841](server.py:7841)) — should pull the actual `balance_transaction.fee` field instead.
- Application fee refund: when refunding a destination-charge PI we should also call `reverse_transfer=True` or use `Application Fee refund` — currently not handled. Means refunding the customer leaves us holding the application fee while the artist's account is debited.

#### 9. Dispute handling — **Partial — needs work**

Webhook handler exists at [server.py:7865](server.py:7865) and sets `status='disputed'`. **What's missing:**

- No admin alert (no email, no Slack, just a status change). Disputes have 7-day deadline; missing one = automatic loss.
- No payout freeze on the connected account.
- No evidence-submission helper.
- No tracking of dispute outcome (`charge.dispute.closed` not handled).

#### 10. Payout schedule — **Missing custom logic**

Stripe's default payout schedule applies (typically daily for Czech accounts after the rolling reserve period). There is no platform override. **Acceptable for MVP**, but the spec mentions "auto-payouts + accounting export" as a B2B sprint — that will need either (a) manual triggers via `stripe.Payout.create` on the connected account, or (b) leave default and just report.

#### 11. Currency / amount handling — **OK**

- DB columns named `*_cents` → haléř (1 CZK = 100 haléř). Consistent.
- Pricing engine uses `Decimal` throughout (no float in money math) — [pricing/economics.py:33](pricing/economics.py:33).
- Stripe API receives `amount` in cents, currency `'czk'` (lowercased on line 6427).
- One minor inconsistency: `total_price` in `create_booking` is computed as `Kč × 100` and stored as `*_cents` but the multiplication uses Python ints — fine, but worth a Decimal pass.

#### 12. Error handling / retries — **Missing**

Pattern is: wrap Stripe call in `try/except stripe.error.StripeError`, return 400/500 with the error string. **No retry layer**, no dead letter queue, no backoff. A transient Stripe 500 → user sees error, must click again. For webhook delivery Stripe itself retries.

#### 13. Test mode — **Partial**

- Live/test split is implicit: if `STRIPE_SECRET_KEY` is empty OR artist has no Connect → demo mode (server.py:6421, 5233). Functional but not clean.
- No automated tests hit the Stripe API (test mode keys not used in CI). The 78 tests skip Stripe entirely.
- Spec calls for "11 test cases listed in the prior pricing spec" — those need to be implemented in Sprint 1.

#### 14. Stripe API version pinning — **Missing**

`grep "api_version"` in server.py: **no results**. Without `stripe.api_version = '2024-XX-XX'`, every new Stripe API release silently changes behavior. **Must be added in Sprint 1**.

#### 15. Card country detection — **Missing**

`pricing/economics.py` accepts a `stripe_card_type` field but every call site passes `'card_eea'` hardcoded ([server.py:5208](server.py:5208)). EU non-EEA and international cards have higher Stripe fees and we're not capturing that → fee tracking is wrong by ~1 % on those.

To fix: parse `payment_method.card.country` from the PI's `payment_method` after retrieval, or webhook on `charge.succeeded` which has `payment_method_details.card.country`.

### Summary of multi-tenancy

`studios` and `studio_members` exist. **Every studio-related query must join through `studio_members`** to get from artist → studio. This is fine for read patterns but **a foot-gun for Sprint 2+ writes**:

- A studio admin viewing "all bookings at my studio" must aggregate across N artists each via their `artist_id`.

## 0.5 Top 5 priority issues

### 1. **CRITICAL — Deposit PaymentIntent is never created** ([server.py:5233](server.py:5233))

Every live-mode booking sits in `pending_payment` forever because no `stripe.PaymentIntent.create()` call is made for the deposit. The frontend has no Elements / Checkout flow either. **The entire deposit-collection path is non-functional in production.** This is Sprint 1 day 1 work.

**Fix:** Add a `POST /api/bookings/<id>/create-payment-intent` endpoint that returns `client_secret`; frontend uses Stripe Elements to confirm; webhook `payment_intent.succeeded` transitions booking to `confirmed`. Add idempotency_key = `f'deposit-{booking_id}'`. **Or** rewrite to separated charges + delayed transfer per the new spec.

### 2. **CRITICAL — No booking state machine; statuses set as string literals**

20+ scattered `UPDATE bookings SET status='...'` calls with no central enum, no allowed-transitions table, no validation. Out-of-order webhooks can corrupt state (e.g., `completed → pending_payment`). With our scale this hasn't bitten yet, but the moment a customer calls about a "completed booking that's pending payment", we have no answer.

**Fix:** Create `pricing/booking_state.py` with explicit `BookingState` enum + `can_transition(from, to)` predicate. Wrap every `UPDATE ... status=...` in a `transition_booking(bid, to_state)` helper that asserts the transition and writes an audit log.

### 3. **HIGH — Multi-tenancy is implicit; no `studio_id` on bookings/slots**

Every B2B query that should be "show me my studio's data" currently routes `artist → studio_members → studio`. This works but is fragile and inefficient at scale. Sprint 2+ will write thousands of queries that all repeat this join. Worse, a misplaced query without the join leaks across studios.

**Fix:** Add `studio_id INTEGER DEFAULT NULL` to `bookings`, `slots`, `portfolio_items`, `reviews`. Backfill from `studio_members`. Add a global helper that asserts `studio_id == session_studio_id` on every B2B endpoint.

### 4. **HIGH — Idempotency keys missing on 4 of 6 mutating Stripe calls**

Balance charges and Connect account creation are not protected. Network retry → duplicate charge or duplicate account.

**Fix:** Add `idempotency_key` to every `stripe.X.create`. Pattern: `f'{operation}-{stable_id}-{actor}'`. Trivial mechanical fix; 1 day of work.

### 5. **HIGH — Dispute handling is observation-only; no alerts, no payout freeze**

A `charge.dispute.created` event marks the booking but does nothing to notify a human or freeze the connected account's payouts. 7-day evidence deadline → silent loss if we're not watching dashboards.

**Fix:** On dispute open: (a) `stripe.Account.modify(payouts={'enabled': False})` to freeze, (b) email + push to admin, (c) Sentry "warning" event, (d) handle `charge.dispute.closed` to unfreeze if won.
